# Integration guide: Health Intelligence Engine <-> Backend <-> n8n <-> Dashboard

> Research prototype. Not a medical device. All data are synthetic (`is_real_astronaut_data: false` in every payload).
> Field-by-field reference: [`JSON_CONTRACT.md`](JSON_CONTRACT.md). Real sample files: `outputs/samples/`.

## 0. What exists vs. what changed (answer to "what is done and what still needs changes")

| Requirement from the n8n side | Status |
|---|---|
| Each astronaut has independent live data, own baseline, history, score, status | **Done** (`engine/live.py`: one `LiveAstronaut` per `astronaut_id`) |
| Analysis keeps running for all astronauts even if the dashboard shows one | **Done** (background simulation advances every astronaut; nothing depends on who is selected) |
| New readings -> report updated (not a static report) | **Done** (report rebuilt after every reading; `latest_reading_at` moves, `generated_at` moves) |
| Report fields: id, generated_at, latest_reading_at, latest vitals, baseline, status, score, severity, needs review, trends, key findings, latest event id | **Done** (`latest_vitals`, `key_findings`, `latest_event_id`, `severity` were added) |

| No new event for every reading of the same continuing anomaly | **Done** (section 5) |
| Metrics behind the alert (observed, baseline, reason for human review) | **Done** (`event.vitals_involved[]`, `event.review_reason`) |
| Offline-first (no Gemini / n8n cloud / internet) | **Done** (section 6) |
| Backend stores readings/analyses/events and runs the outbox | **Backend's job**; the engine exposes pull endpoints and an optional push (section 7) |
| "Who runs the simulation" | **Decision needed** (section 7). Default: the engine runs it |

## 1. Endpoints (base `http://localhost:8000`, Swagger at `/docs`)

Start: `uvicorn api_server:app --port 8000`. Environment variables (all optional):
`HEALTH_SIM_AUTOSTART=1` (start the simulation at boot), `HEALTH_SIM_INTERVAL=1.0` (seconds per round),
`HEALTH_START_STEP=576`, `HEALTH_ASTRONAUT_COUNT=6` (4 by default, max 7), `HEALTH_PUSH_URL=<local backend url>`.

| Endpoint | Purpose |
|---|---|
| `GET /health` | liveness, `needs_internet: false`, astronaut list, `engine_instance_id` |
| `POST /api/v1/simulation/start?interval_seconds=1&astronaut_ids=&start_step=` | start continuous simulation (all astronauts by default) |
| `POST /api/v1/simulation/stop` / `GET /api/v1/simulation/status` / `POST /api/v1/simulation/reset?start_step=&astronaut_id=` | control / progress |
| `GET /api/v1/astronauts` | one line per astronaut: status, severity, score, latest_reading_at, latest_event_id (for the 4-6 astronaut wall) |
| **`GET /api/v1/report?astronaut_id=`** | latest live report (n8n Tool 1) |
| **`GET /api/v1/events?astronaut_id=&review_only=true&status=ALL\|OPEN\|RESOLVED`** | incidents of that astronaut (n8n Tool 2) |
| `GET /api/v1/events/feed?since_seq=&astronaut_id=&event_type=&limit=&engine_instance_id=` | ordered, replayable stream of event messages, all astronauts (for the backend / Workflow 01). Cursor: `next_since_seq` (see 6b) |
| `GET /api/v1/live/ticks?astronaut_id=&since_seq=&limit=&engine_instance_id=` | every reading with its per-reading analysis (backend persists this as history). Cursor: `next_since_seq` (see 6b) |
| `POST /api/v1/live/ingest` | backend-owned data source: send one raw reading, it is analysed immediately |
| `POST /api/v1/analyze`, `POST /api/v1/evaluate-instant` | stateless helpers |
| `GET /api/v1/simulate/next`, `POST /api/v1/simulate/reset` | older manual single-step endpoints, kept |

Timing: step = 5 simulated minutes. With `interval_seconds=1` and 4 astronauts the engine needs about 0.3 s of compute per round
(about 0.5 s with 6), so 1 s per round is safe. 1 simulated hour = 12 s, 1 simulated day = about 4.8 min.
Use `interval_seconds=0.25` to fast-forward the demo.

## 3. Dictionary: statuses, severities, event types

**Report `status`** (looks at the last 3 hours only):

| Value | Meaning |
|---|---|
| `NOMINAL` | within the astronaut's own time-of-day baseline (one isolated 3-sigma reading is treated as noise) |
| `MONITOR_CLOSELY` | at least 2 flagged readings in 3 h, or sleep below baseline for 2+ nights. No human review requested |
| `REVIEW_REQUIRED` | an alert happened in the last 3 h: 3 consecutive flagged readings, or one reading beyond 4 sigma. `needs_human_review = true` |
| `INSUFFICIENT_DATA` | stream unusable now (more than 30 min of consecutive invalid readings, or more than 25 % of the last 3 h). No health conclusion is drawn |

**Severity** (report `severity` = severity of the active incident, or `NONE`; event `severity`):

| Value | Meaning |
|---|---|
| `NONE` | no active incident |
| `LOW_DEVIATION` | noise-level (a short run below the review threshold). Never emitted as an event |
| `MODERATE_DEVIATION` | reached review threshold (3+ flagged readings) but peak below 4 sigma |
| `HIGH_REVIEW_PRIORITY` | peak at or above 4 sigma (anomaly_score >= 0.67), or deviation lasting 3+ hours |

**Incident `type`**: `ACUTE_DEVIATION` (shorter than 3 h) and `SUSTAINED_DRIFT` (3 h or longer).
**Incident `status`**: `OPEN`, `RESOLVED`. **Sleep status**: `NOMINAL`, `SHORT_SLEEP_WATCH`, `SLEEP_RESTRICTION_TREND`, `INSUFFICIENT_DATA`.

**Event messages (`event_type`)**:

| `event_type` | When | How often |
|---|---|---|
| `HEALTH_REVIEW_REQUIRED` | a new incident reaches the review threshold | once per incident |
| `HEALTH_EVENT_ESCALATED` | same incident became HIGH priority or turned into a sustained drift | at most twice per incident |
| `HEALTH_EVENT_RESOLVED` | no flagged reading for more than 30 min of non-exercise time | once per incident |

Workflow 01 currently handles `HEALTH_REVIEW_REQUIRED`. Filter on `event_type` so the other two are routed (update the existing incident) or ignored.

`anomaly_score` is a deviation scale (`min(1, deviation/6)`), **not** a probability: 0.5 = 3 sigma, 0.67 = 4 sigma, 1.0 = 6 sigma or more.

## 4. How baseline, anomaly detection and trends update with live data

* **Baseline**: fitted once per astronaut on the first 48 h of readings (calibration), as a 24 h rhythm + sleep effect per vital.
  It is **frozen** afterwards: it is not re-fitted from live data, so a slow drift cannot "become normal". (Re-calibration in flight is future work.)
* **Anomaly detection**: each new reading is validated, compared with the astronaut's expected value for that time of day, scored with
  the z-score, the 1 h rolling trend and the Isolation Forest, and combined (hybrid). Runs per reading (about 20 ms).
* **Trend analysis**: slope of `value - expected` over the last 3 h, recomputed after every reading; sleep is re-evaluated each morning
  over all nights since calibration.
* **Report**: rebuilt after every reading from the last 36 h window plus the full incident history. `latest_vitals` is the last reading.
  `data_quality` in a live report describes the last 36 h window.
* **Events**: built incrementally by the tracker; it produces exactly the incidents that a batch analysis of the same data finds
  (checked by `tests/test_live.py::test_live_events_equal_batch_events`).

## 5. How the engine avoids creating many events for one continuing anomaly

1. While an incident is open, every further flagged reading is merged into the same incident (same `event_id`).
2. The incident closes only after more than 30 min of non-exercise readings without a flag. Planned exercise does not split an incident.
3. Only incidents that reach the review threshold are emitted. Single noisy readings stay internal.
4. One `HEALTH_REVIEW_REQUIRED` per incident; later changes are `ESCALATED` (max 2) or `RESOLVED` (1).
5. Every message has `emission_id` (idempotency key, e.g. `ASTRO_01-EV-20261114T0500:HEALTH_REVIEW_REQUIRED`). If you receive the same
   `emission_id` twice, ignore the second one.
6. In a 20-reading incident (ASTRO_01, step 780) the feed contains exactly 2 messages: REVIEW_REQUIRED, then RESOLVED.

Real numbers: in a 5-day synthetic run, chance (non-injected) review-level incidents appear at about 0.2 to 0.7 per astronaut per day
(see `outputs/evaluation_report.md`). Expect an occasional incident in a "healthy" astronaut during the demo, and plan the Incident
workflow for that.

## 6. Offline-first

* The engine needs no internet, no Gemini and no n8n: generation, analysis, detection, reports and events all run in-process.
* Events are kept in memory (`/events/feed`) and appended to a local log `data/live/events.jsonl` (one JSON per line).
* `HEALTH_PUSH_URL` (optional) pushes each message to the local backend in a background thread, best-effort. If the backend is down the
  push is dropped and analysis continues; the backend catches up with `GET /events/feed?since_seq=<next_since_seq it stored>`.
* The Earth link only matters to the backend's outbox/dispatcher; the engine does not know about it.
* After an **engine restart** the in-memory feed starts empty and `engine_instance_id` changes. The log file keeps the history on disk
  but is not re-served by the API, so the backend should persist events as they arrive (it should anyway, for the outbox).

## 6b. Pull cursors: how the backend gets every reading and event exactly once

**Readings** (`GET /live/ticks?astronaut_id=&since_seq=&limit=`)
* Every tick has `tick_seq` (1, 2, 3 ... per astronaut, **never goes back**, not even after `simulation/reset`) and `run`.
  `step_index` is only the position in the replay data and **does go back** after a reset: never use it as a cursor.
* Request: `since_seq`, `limit`, `engine_instance_id` (the one you stored). Response: `{astronaut_id, engine_instance_id, instance_changed, run, last_tick_seq, next_since_seq, has_more, count, gap_detected, ticks[]}`.
  `tick_seq` restarts at 1 when the **engine** restarts, so key stored ticks by `(engine_instance_id, astronaut_id, tick_seq)`; `instance_changed=true` means the engine restarted and the ticks are served from the beginning.
  Store `next_since_seq` after you have saved the page; send it as `since_seq` next time. Start with `since_seq=0`.
  If `has_more` is true, call again immediately. De-duplicate on `(astronaut_id, tick_seq)` (a retry after a crash returns the same ticks).
* The engine keeps the last 5000 ticks per astronaut in memory (about 17 days at 5 min). `gap_detected=true` means readings between your
  cursor and the oldest kept one were already dropped (the backend was away too long).
* A reset does not delete the buffered ticks; they stay readable with their old `run`.

**Events** (`GET /events/feed?since_seq=&limit=&engine_instance_id=`)
* Response: `{engine_instance_id, instance_changed, last_sequence, next_since_seq, has_more, count, events[]}`.
* Use `next_since_seq` as the cursor, **not** `last_sequence`. `last_sequence` is the end of the whole feed; when a page is cut by
  `limit`, `next_since_seq` is the sequence of the last message actually returned, so nothing is skipped. (With filters too.)
* Always send the `engine_instance_id` you stored. If the engine restarted, sequences start again at 1: the response then has
  `instance_changed=true` and is served from 0, so the backend knows to store the new instance id and de-duplicate on `emission_id`
  (the events log `data/live/events.jsonl` is not re-served).
* De-duplicate on `emission_id` (idempotency key), whatever the delivery path (pull or push).

## 7. Who runs the simulation and who stores what (needs a decision with Abdelrahman)

Proposal (default, nothing extra to build):

| Piece | Owner |
|---|---|
| Generate readings, run analysis, build reports and events | Engine (`simulation/start`, or `HEALTH_SIM_AUTOSTART=1`) |
| Save readings/analyses (history) | Backend polls `GET /live/ticks?since_seq=<next_since_seq>` per astronaut every few seconds and writes SQLite |
| Save events, outbox, dispatch to n8n, sync to Earth | Backend polls `GET /events/feed?since_seq=` (or receives pushes), then does the rest |
| Reports for the dashboard | Backend proxies `GET /report` / `GET /astronauts` (always the latest) |

Alternative: Abdelrahman owns the simulator or a real telemetry source and sends each reading to `POST /api/v1/live/ingest`. The
engine analyses it and returns the tick; events still go to the feed. Use **one** source per astronaut, never both.

## 9. Mapping to the agreed event example

| Agreed example | Engine |
|---|---|
| `schema_version`, `event_type`, `source`, `event_id`, `astronaut_id`, `data_source` | same names and meaning |
| `event_type: HEALTH_REVIEW_REQUIRED` | same; plus `HEALTH_EVENT_ESCALATED` and `HEALTH_EVENT_RESOLVED` |
| `event_id: ASTRO_01-EV005` | `ASTRO_01-EV-20261114T0500` (astronaut + start time of the incident: stable, unique, the same however often it is re-sent; after a simulation reset it gets the suffix `-r2`, `-r3`...) |
| `created_at` | the reading (mission) time of the message, UTC with `Z`. The wall-clock time is in `emitted_at` |
| `event.type / severity / needs_human_review / anomaly_score / duration_minutes / explanation` | same, `needs_human_review` Boolean, `anomaly_score` Number, `duration_minutes` Number (grows while the incident is open) |
| *(new)* | `emission_id`, `sequence`, `engine_instance_id`, `run`, `event.status`, `event.review_reason`, `event.vitals_involved[]` (vital, direction, `observed_mean`, `expected_mean`, `baseline_sigma`, `mean_zscore`, `peak_zscore`), `event.triggered_by`, `event.start`, `event.end`, `event.flagged_readings`, `event.peak_zscore` |
| `explanation` (one sentence) | longer, generated from the numbers, always names the vitals, their z-scores and the baseline used |

`event.scenario_context_demo_only` is the simulator's label. It is for narrating the demo only, never use it in logic.

## 10. Known limits / not done

* The in-memory feed does not survive an engine restart (see sections 6 and 6b: `instance_changed` tells the backend).
* Baseline is frozen after calibration; no re-calibration.
* Alerts include chance incidents (see section 5); the thresholds are in `engine/config.py`.
* `api_server.py` could not be run with real FastAPI in the authoring sandbox. Its handlers were exercised directly (with stand-in stubs
  for FastAPI) and the whole engine behind them is covered by tests. Run `uvicorn api_server:app` and open `/docs` once to confirm.
* No authentication and CORS is open (local hackathon setup).
* Gemini should explain these fields only. The engine never diagnoses and never recommends treatment; make the agent's system prompt say the same.
