## v2.1: live, multi-astronaut integration (requested by the n8n / backend side)

| Request | Change |
|---|---|
| Independent live data per astronaut, analysis for all even if one is selected | `engine/live.py` (`LiveSystem`, `LiveAstronaut`); background simulation advances every astronaut; `HEALTH_ASTRONAUT_COUNT=6` for six |
| Continuous analysis, report must not stay static | report rebuilt after every reading; new fields `latest_reading_at`, `latest_vitals`, `severity`, `key_findings`, `latest_event_id` |
| Health events with stable unique ids, one per incident | `EventTracker`: incident merged while open, 3 message types, `emission_id` idempotency key; event ids are `<astronaut>-EV-<start time>` |
| Metrics behind the alert | `event.vitals_involved[]` (observed, expected, sigma, mean z, peak z) and `event.review_reason` |
| Offline-first | no internet dependency; in-memory feed + local `data/live/events.jsonl`; optional best-effort push; `GET /events/feed?since_seq=` for catch-up |
| Backend can persist history | `GET /live/ticks?since_seq=` (cursor `next_since_seq`, see INTEGRATION 6b); `POST /live/ingest` if the backend owns the data source |
| Docs for the other teams | `docs/INTEGRATION.md`, `outputs/samples/*.json` (generated by the real engine) |

Breaking changes for anyone who already integrated v2.0: event ids changed from `EV001` sequence numbers to start-time based ids;
`GET /api/v1/events` now reads the live incident list (`status` field added); `GET /api/v1/report` returns the *live* report.

## Known issues / not done
* The live event feed is in memory (see `docs/INTEGRATION.md` section 6); the baseline is frozen after calibration.
* False-alarm rate is high (0.73/astronaut-day on the blind astronauts). Raising `ALERT_MIN_CONSECUTIVE` / `ALERT_Z_OVERRIDE` should help but was **not** applied because it would need a new blind set to validate.
* `api_server.py` was written against FastAPI/pydantic but could not be run end-to-end in the authoring sandbox (no FastAPI installed there): its endpoint logic was exercised through stubs only. Run `uvicorn` once and open `/docs` before 14 Nov.
* Libraries were tested with pandas 3.0.6; `requirements.txt` pins pandas 3.1.1 (the version from your `.venv`). Run `python tests/test_engine.py` after installing.
* Skin temperature / SpO2 / respiration have no literature source yet (`docs/RESEARCH.md`).
* `demo_notebook.ipynb` was rewritten for v2; its code cells were executed as a script in the sandbox (all ran), but not inside Jupyter itself.

## Pull-cursor fixes (integration review)

| Problem | Fix |
|---|---|
| `/live/ticks` used `since_step`; `step_index` goes back after a `simulation/reset`, so a backend that had read up to 1400 would miss every new tick | Every tick has `tick_seq` (monotonic per astronaut, never reset) and `run`; endpoint uses `since_seq`; response has `next_since_seq`, `has_more`, `gap_detected`. Reset no longer clears the tick buffer. **Breaking:** `since_step` was removed; the response is now an object with `ticks[]` |
| `/events/feed` returned the global `last_sequence`; a backend that used it as cursor after a page cut by `limit` skipped events | Response has `next_since_seq` (last returned sequence when `has_more`, else end of feed) and `has_more`. `last_sequence` kept for information |
| Engine restart restarted `sequence` at 1 without the backend noticing | Optional `engine_instance_id` query; response has `instance_changed` and is served from 0 when it differs |

New tests: `tests/test_live.py` (5): cursor survives reset, tick paging, feed paging with limit, feed paging with filter, restart detection.
